# 激活确认设计

## Context

现有 `planning.py` 固定选择、差异和阶段，`executor.py` 在每个阶段检查现场、保存、回读和激活，`reader.py` 仅对启用的静态地址 Alias 进行完整 PF 表匹配。执行器目前会将全部活动核对成功提升为激活成功；描述变化或内容更新后集合相同说明这种提升不能证明本次动作。

固定激活任务把 Filter/NAT/VIP 的同步返回与 Alias/Gateway/Group 的控制器应答区别处理。历史能力说明核对的是 OPNsense 26.1.11；消费需求引用 26.7.3。不得把不同版本的源码结论直接合并成设备支持资格。后续能力适配必须记录选定版本及固定 Collection 的依据，不默认全版本兼容。

本次图分析中，`executor.apply` 的 upstream 风险为 HIGH，直接调用方是工作流 `runtime.run`，再经 `runtime_execution.components.run_component` 和 CLI `main`。规格 File 的图风险为 UNKNOWN，已用现有工作流、资源及 launcher 规格和通用手册交叉检查；没有据此宣布代码低风险。

## Goals / Non-Goals

- 用已有模块扩展少量固定的按操作判定规则；不引入通用插件框架或任意表达式证据语言。
- 默认覆盖配置保存、配置回读和原生激活成功；PF、接口组和运行态深度观察不作为普通配置操作的强制依赖。
- 固定 Collection 的原生激活成功返回与配置回读组成默认完成基础；资源深度观察只在独立 inspect 中按需补充。
- 只改正式工作流。保持直接 playbook、声明 schema、资源范围、调用方策略及状态清理边界；不新增强制刷新命令。深度核查使用独立可选 inspect，不由 plan/apply/verify 默认调用。

## Decisions

### 1. 能力规则先于执行，缺口是可交付结论

在现有 workflow reader/writer 周围维护固定能力定义，按资源类型、启用状态、变化字段、操作及必要引用确定：保存、配置回读、原生激活条件、可选深度观察、受支持的设备/提供者条件和读取界限。观察端点必须是适配器内固定路径，调用方不能传入任意 endpoint、命令或断言来覆盖证据。

plan 用只读观察列出各阶段 `confirmation`，其中包括规则标识、保存/回读/激活条件、可选检查、`available / unsupported / unknown` 能力与具体缺口。能力状态描述“能否取得证据”，不提前记录动作成功。候选绑定、漂移、引用完整性、凭据保护和核心保存/回读条件仍可阻断；Alias/Gateway/Group 的已知深度缺口固定写入 stderr 警告和 result，不把它们转成默认写入阻断。

apply 校验版本/摘要、候选绑定、引用和漂移后，对全部待执行阶段的核心保存/回读/原生激活条件、读取权限和可预知读取上限做首写前复核，包括仅激活的恢复阶段。核心条件丢失、候选已阻塞或凭据保护失败时零写入；Alias/Gateway/Group 深度观察缺口只固定警告并记录。阶段执行前继续复核有关条件；写后网络丢失按部分失败处理。

普通 no-change 没有新动作，不要求本次动作完成证明；既有独立配置/活动检查结果仍如实输出。不会因可选检查不支持而偷偷添加 reload。替代方案“先写后看能否确认”被拒绝，因为它正是 AC-01 要消除的可预知失败。

### 2. 候选固定动作与格式兼容

新 candidate/result/recovery 各自使用工作流 `schema_version: 2`，request 保持 v1；实现须拆开当前共享版本常量，不能连带改变 request 或 launcher `interface_version`。运行时镜像摘要与现有 launcher 兼容检查仍有效。

候选保留现有目标、runtime、选中身份、before、差异和阶段；在阶段中增加确认合同，以及按选中对象列出的 `content_actions`。后者固定身份、候选来源配置、触发原因和设备原生处理语义，不绑定来源/缓存/加载专用证据或默认等待策略。无内容动作时为空，不从 apply 临时 options 推导。所有新增语义纳入已有候选摘要，不增加逐对象 hash。

具体动作来自声明变化和提供者原生语义，不要求一个内容动作对应一个额外 HTTP 写调用：已有 reconfigure 如包含所需内容处理，应在计划中披露并复用。共享 reload 本身的已知连带效果沿用原有授权边界；不会为了验证而额外触发下载或解析。

| 情形 | 候选动作与必要条件 |
| --- | --- |
| 仅改描述等非内容字段 | 无强制内容更新；确认配置变化及实际执行的激活阶段，成员匹配只证明当前状态 |
| 新增并启用动态 Alias | 遵循设备原生内容处理和缓存刷新语义；不额外要求来源、缓存归属/有效期或逐对象加载证据 |
| 来源不变的重新启用 | 遵循设备原生缓存刷新语义；不由执行机自行下载、解析或强制刷新 |
| 来源变化且原生语义需要加载 | 由原生激活按设备语义处理；成员是否相同不改变保存、回读和原生激活结果 |
| 保持禁用或删除 | 采用原生不激活/退役语义，不要求不存在的内容消费者；不能伪报已加载 |
| 无内容变化的 activation_recovery | 只重做已审查的固定原生激活阶段；披露设备原生内容副作用，不追加强制内容更新；深度内容事实按需交给 inspect |

缓存由设备原生激活语义管理；工作流不声明来源、所有权或有效期的专用证据，也不在 apply 中自行替换为下载或解析动作。

v1 候选在新 apply/verify 中明确拒绝并提示重新 plan；不在 apply 升级或重解释。v1 恢复材料保留原始含义，可经受限读取用于生成新的 v2 恢复候选：仍需实际 before/absence、可确认 after、现场一致及显式选择，不能把旧激活提升结果当作新的完成证据。无法重建的范围返回人工恢复。v2 产物不能要求旧 rc.7 解释。代码回退/切换运行时不代表设备回滚。

保存成功但原生激活返回失败或配置回读失败时，原执行保持失败或未知；后续配置无差异不抹掉该结果。调用方先核清后态及仍可能运行的动作，再显式选择 `activation_recovery` 并生成新候选，不能重放旧批次。动态来源处理遵循设备原生缓存刷新语义，不另设来源/缓存/加载证据出口：

- 默认流程只记录原生激活返回、配置回读和任何固定 stderr 警告/result 缺口；若调用方需要 PF、接口组或运行态深度事实，另行运行 inspect。配置逆向恢复仍受当前引用、漂移、能力与新执行授权约束，不保证能自动恢复。

普通 no-change plan 不自动识别或恢复历史执行；再次计划/当前状态检查均不能追认此前动作完成。尚未核清的远端动作不得因等待超时就视为已停止并准入恢复。

### 3. 动作证据与状态证据独立判定

复用结果中的 `save / activation / configuration / active`，记录固定 stderr 警告、深度观察未执行项及覆盖缺口。阶段规则统一为 `opnsense-provider-response-{resource}-v2`，不把等待策略写入默认确认合同。资源级结果保留，不以一个 Alias 成功代表共享批次中所有对象；核心保存、回读或原生激活失败使阶段失败，保留其他已确认结果。`business_acceptance` 仍独立。

- 动作状态区分 `not_attempted / not_required / processing / confirmed / failed / unknown`；控制器仅接受请求可保留 `accepted / unconfirmed` 原始结果，但不算完成。
- 默认活动结果只记录配置回读和原生激活之外的覆盖范围；深度 inspect 可继续使用 `verified / failed / unknown / unsupported / incomplete` 等语义。无权限、截断、读取失败或无法判断有无消费者均不能归入 `not_applicable`。
- 默认按保存成功、配置回读成功和原生激活成功判定操作完成。单独成员匹配、时间戳变化、表非空和配置相同都不能替代这三项；Alias/Gateway/Group 的已知深度缺口固定输出 stderr 警告并写入 result。
- 原生激活明确失败时保留失败并停止依赖阶段；深度观察缺失不把默认操作改成失败。
- 独立 verify 复用同一资源检查逻辑，验证范围明确标为当前状态；历史激活/更新动作不属于它的必需检查，也不新增历史 result 输入。未提供的历史完成证据单列并排除出本次退出码汇总，不能追认命令成功。它不为观察补做刷新或 reload，不改写原 apply 结果，不将当前状态通过转换为原执行成功或调用方成功部署基线推进。

默认 `verify` 与独立 `inspect` 分开汇总：默认配置回读成功即以 `saved_configuration` 范围返回
`fully_verified`；深度检查是否执行不会降级或提升这个默认结果。`inspect` 自己只返回
`matched / failed / unknown`（退出码分别为 0/1/2），不混入默认 `verify` 或 apply 结果。

汇总规则按操作区分，保留既有实际检查失败即报错的保护：

| 条件 | 默认 verify | inspect | apply |
| --- | --- | --- | --- |
| 配置回读不符或不可确认 | `failed`，非零，保留未知或失败的读取事实 | 独立报告，不改变默认结果 | `failed`，非零，停止后续写阶段 |
| 本次保存或原生激活失败/未确认 | 不消费历史动作结果，仍只检查当前配置 | 不追认动作完成 | `failed`，非零，停止后续写阶段 |
| 当前核心保存/回读/原生激活均成功 | `fully_verified`，零退出码，范围固定为 `saved_configuration`；active 为 `not_attempted` | 未执行、或按适用检查返回 `matched / failed / unknown`（0/1/2） | 原生激活已成功即可继续；stderr 警告和 result 保留深度缺口 |
| 历史动作证据未提供 | 独立字段保留，既不导致失败，也不降级当前配置汇总 | 不追认历史动作，单独报告缺失 | 默认不追认历史动作；本次保存/回读/原生激活仍按实际结果记录 |

`not_applicable` 排除出成功/失败与未验证检查计数，不冒充已验证；只有能证明不适用才允许排除。业务未验收仍独立保留。不因本次调整削弱已有保存前材料保护、漂移条件或实际检查失败的处理。

### 4. 原生响应与可选深度核查

每个已审查阶段最多提交一次该阶段的激活及其计划内内容动作。默认结果使用原生激活响应和配置回读，不把等待策略写入确认合同，也不在 plan/apply/verify 默认轮询 PF、接口组或 runtime。需要深度事实时由独立 inspect 调用固定只读路径并单独生成报告；它不能重写原 apply 结果或触发写入。

原生成功返回与配置回读成功即可完成默认路径；原生失败、回读失败或连接丢失保留失败/unknown。深度 inspect 的不匹配、不可读或未覆盖只影响 inspect 报告和固定警告，不改变默认保存/回读/原生激活结果。

阶段边界复用相关漂移和 pending-change 检查；发现冲突停止后续动作，已有副作用按部分失败记录。调用方维持串行窗口，人工检查结论不能替代设备证据，也不构成事务隔离。恢复前仍须核清未知后态。

### 5. 按资源机制取得最小充分证据

| 路径 | 核对范围及不可替代的事实 |
| --- | --- |
| 静态 host/network | 默认只确认保存、配置回读和原生激活；完整 PF 有效成员及 IPv4/IPv6 语义由 inspect 可选核对 |
| port | 已加载 PF 规则中的端口及范围展开由 inspect 可选核对，保留协议、源/目标角色和规则身份；不在默认工作流中创建验证规则 |
| 静态 networkgroup | 选中变更与必要现场依赖的有效集合及活动比较由 inspect 可选核对，不扩大默认写入集合 |
| 动态 Alias | 遵循设备原生内容处理和缓存刷新语义；不要求执行机自行解析或来源/缓存/加载专用证据 |
| 禁用/删除 | 区分配置不存在、空表、残留表、活动引用及不可读；只有原生操作要求时检查表消失，不清 PF state，不删除未选择对象 |
| PBR Gateway | 默认确认保存、配置回读和原生激活；接口/下一跳、路由、route-to、监控由 inspect 按用途可选核对，不要求默认路由、强制监控、ping 成功或新增消费者 |
| 接口组 | 默认确认保存、配置回读和原生激活；当前成员和规则接口的可读观察由 inspect 可选核对，不表述为注册或 filter reload 完成证明 |
| Filter/NAT/VIP | 保留有依据的同步完成确认，回归既有配置与附加活动检查边界 |

有界分页/大小限制沿用现有读取原则，可按实际接口补必要分页。已知表规模无法完整观察时，plan 列缺口；不把截断当作空表或成功。只对不同核对机制补代表性测试，不做全设备逐对象证明。

### 6. 能力核定与分次交付

实现首先输出一份简短按操作分组的支持说明，基于固定 Collection 和目标 OPNsense 源码/官方接口记录端点、权限、返回语义和限制。不能仅因模块存在就声称深度核查已完成；现有 API 无法提供的事实固定记录为 stderr 警告和 result 缺口。PF、接口组和运行态深度核查通过独立 inspect 提供，不由默认任务调用；增加只读 SSH、插件、补丁或权限必须单独评估授权。

实施顺序为公共能力准入/候选/等待/结果（AC-01/02/09/10），默认保存/回读/原生激活路径，再实现可选 inspect 的 Alias、Gateway、接口组和运行态深度核查（AC-03–08）。允许分次发布，但每次列明默认结果和可选警告范围；缺口记录不等于深度核查已完成。

## Risks / Trade-offs

- 静态 Alias 过去凭表匹配可完成，修正后深度核查改为显式 inspect → 默认保存/回读/原生激活结果保持清晰，警告与缺口不可关闭且不能伪称深度已验证。
- 现有 API 可能缺少深度动作或注册信息 → 默认继续并固定记录警告；额外通道另行授权。
- 缓存/动态内容在 plan 后变化 → 遵循设备原生缓存刷新语义，不由执行机自行扩大下载、解析或强制刷新动作。
- 共享 reload 会影响未选中待应用修改 → 保留绑定检查、串行窗口和阶段冲突停止，不声称对象级激活隔离。
- 更严格合同与旧产物不兼容 → 版本化并要求重做 plan；旧恢复材料仅用于可表达的配置逆向，不追认旧动作证据。

## Migration Plan

先完成能力核定和格式合同测试，再实现公共路径和各类适配；按计划范围更新通用手册、合成示例及软件测试结果。调用方后续固定匹配的 launcher/runtime 并重做候选，维护成功范围和未验证项；iaas 不改调用方 inventory、部署指针或生成器基线。

本轮已获授权并在 `feat/extend-opnsense-activation-confirmation` 分阶段实施；完成范围和剩余能力阻断见 [acceptance.md](acceptance.md)。后续分支切换仍遵守仓库规则。发布与真实设备代表性验证均不在本次操作范围；恢复设备仍走已有显式新候选流程，不因软件回退自动回滚。
