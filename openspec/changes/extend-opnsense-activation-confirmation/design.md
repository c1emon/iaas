# 激活确认设计

## Context

现有 `planning.py` 固定选择、差异和阶段，`executor.py` 在每个阶段检查现场、保存、回读和激活，`reader.py` 仅对启用的静态地址 Alias 进行完整 PF 表匹配。执行器目前会将全部活动核对成功提升为激活成功；描述变化或内容更新后集合相同说明这种提升不能证明本次动作。

固定激活任务把 Filter/NAT/VIP 的同步返回与 Alias/Gateway/Group 的控制器应答区别处理。历史能力说明核对的是 OPNsense 26.1.11；消费需求引用 26.7.3。不得把不同版本的源码结论直接合并成设备支持资格。后续能力适配必须记录选定版本及固定 Collection 的依据，不默认全版本兼容。

本次图分析中，`executor.apply` 的 upstream 风险为 HIGH，直接调用方是工作流 `runtime.run`，再经 `runtime_execution.components.run_component` 和 CLI `main`。规格 File 的图风险为 UNKNOWN，已用现有工作流、资源及 launcher 规格和通用手册交叉检查；没有据此宣布代码低风险。

## Goals / Non-Goals

- 用已有模块扩展少量固定的按操作判定规则；不引入通用插件框架或任意表达式证据语言。
- 覆盖必要的当前配置、动作完成和活动状态，不把业务连接测试变成普通配置操作的强制依赖。
- 固定 Collection 的成功返回足以证明某阶段时直接使用；只有缺少该证据或操作另有要求时才补必要观察。
- 只改正式工作流。保持直接 playbook、声明 schema、资源范围、调用方策略及状态清理边界；不新增强制刷新命令。

## Decisions

### 1. 能力规则先于执行，缺口是可交付结论

在现有 workflow reader/writer 周围维护固定能力定义，按资源类型、启用状态、变化字段、操作及必要引用确定：激活目标、必要证据、可选观察、受支持的设备/提供者条件和读取界限。观察端点必须是适配器内固定路径，调用方不能传入任意 endpoint、命令或断言来覆盖证据。

plan 用只读观察列出各阶段 `confirmation`，其中包括规则标识、所需证据、可选检查、`available / unsupported / unknown` 能力与具体缺口。能力状态描述“能否取得证据”，不提前记录动作成功。必要能力未知或不支持时，保留可审查差异和阻塞原因，返回非零；如保存候选，候选必须明确 `blocked`，不能被 apply 当作可执行计划。可选检查未知仅记录未覆盖项。

apply 校验版本/摘要和漂移后，对全部待执行阶段的必要能力、读取权限和可预知读取上限做首写前复核，包括仅激活的恢复阶段。必要能力丢失、候选已阻塞或所需证据超出可用界限时零写入。阶段执行前继续复核有关条件。检查只证明能力与前置状态，不保证未来调用成功；写后网络丢失按部分失败处理。

普通 no-change 没有新动作，不要求本次动作完成证明；既有独立配置/活动检查结果仍如实输出。不会因可选检查不支持而偷偷添加 reload。替代方案“先写后看能否确认”被拒绝，因为它正是 AC-01 要消除的可预知失败。

### 2. 候选固定动作与格式兼容

新 candidate/result/recovery 各自使用工作流 `schema_version: 2`，request 保持 v1；实现须拆开当前共享版本常量，不能连带改变 request 或 launcher `interface_version`。运行时镜像摘要与现有 launcher 兼容检查仍有效。

候选保留现有目标、runtime、选中身份、before、差异和阶段；在阶段中增加确认合同，以及按选中对象列出的 `content_actions`。后者固定身份、候选来源配置、触发原因、`initialize / update / reuse_cache` 动作、缓存适用条件、必要完成/加载证据及有限等待策略。无内容动作时为空，不从 apply 临时 options 推导。所有新增语义纳入已有候选摘要，不增加逐对象 hash。

具体动作来自声明变化和提供者原生语义，不要求一个内容动作对应一个额外 HTTP 写调用：已有 reconfigure 如包含所需内容处理，应在计划中披露并复用。共享 reload 本身的已知连带效果沿用原有授权边界；不会为了验证而额外触发下载或解析。

| 情形 | 候选动作与必要条件 |
| --- | --- |
| 仅改描述等非内容字段 | 无强制内容更新；确认配置变化及实际执行的激活阶段，成员匹配只证明当前状态 |
| 新增并启用动态 Alias | 按候选来源首次获取/解析及加载；合法空内容必须有成功的处理证据 |
| 来源不变的重新启用 | 确认加载；只有能证明当前来源和有效期等条件且候选允许时复用缓存，否则计划更新并确认 |
| 来源变化且原生语义需要加载 | 按新来源更新及加载，拒绝旧来源缓存；成员相同不取消动作 |
| 保持禁用或删除 | 采用原生不激活/退役语义，不要求不存在的内容消费者；不能伪报已加载 |
| 无内容变化的 activation_recovery | 只重做已审查激活阶段，不能追加强制内容更新；内容前置条件不满足则报告缺口并重新计划，必要时保持阻塞 |

缓存条件须在 apply 首写前重新核对。若计划允许的缓存已过期，不自动改成下载，返回重新计划要求。没有足够证据证明来源和有效性时不允许复用。

v1 候选在新 apply/verify 中明确拒绝并提示重新 plan；不在 apply 升级或重解释。v1 恢复材料保留原始含义，可经受限读取用于生成新的 v2 恢复候选：仍需实际 before/absence、可确认 after、现场一致及显式选择，不能把旧激活提升结果当作新的完成证据。无法重建的范围返回人工恢复。v2 产物不能要求旧 rc.7 解释。代码回退/切换运行时不代表设备回滚。

### 3. 动作证据与状态证据独立判定

复用结果中的 `save / activation / configuration / active`，补 `content_update`、必要证据依据及覆盖缺口。资源级结果保留，不以一个 Alias 成功代表共享批次中所有对象；一个必要子动作失败使阶段失败，保留其他已确认结果。`business_acceptance` 仍独立。

- 动作状态区分 `not_attempted / not_required / processing / confirmed / failed / unknown`；控制器仅接受请求可保留 `accepted / unconfirmed` 原始结果，但不算完成。
- 活动观察继续使用 `verified / failed / unknown / unsupported / incomplete` 等既有语义；无消费者的检查单列 `not_applicable` 和原因，不填 `verified`。
- 按操作组合判定：可信的同步完成返回，或可关联本次动作的完成结果加必要活动回读。单独成员匹配、时间戳变化、表非空和配置相同都不能通用提升激活状态。
- 必要刷新成功但成员未变，动作与内容可分别成功；刷新明确失败而旧内容仍匹配，保留成员匹配，动作仍失败，不继续后续写阶段。
- 独立 verify 复用同一资源检查逻辑，仅报告当前状态；没有历史完成证据时保留历史动作未知/未提供，不能追认命令成功。它不为观察补做刷新或 reload。

必要失败/未知返回非零并停止后续写阶段；必要证据成功而仅可选活动检查不支持时允许 `completed_with_unverified`。不因本次调整削弱现有失败停止、保存前材料保护或漂移条件。

### 4. 有界只读等待

每个已审查阶段最多提交一次该阶段的激活及其计划内内容动作，之后只轮询固定只读接口。采用单调时钟、阶段总时限、尝试次数上限和有限单请求超时；默认总等待 60 秒、最多 30 次观察、间隔 2 秒，单请求及间隔均受剩余期限约束。能力规则可选择更小预算；改变候选预算需要重新计划，不提供无限等待或 apply 临时延长。

明确完成返回立即结束；明确操作失败立即失败，不靠随后匹配的表掩盖失败。处于已知传播窗口的暂未匹配可继续观察；不能从不匹配直接推断正在处理。耗尽预算而缺少完成证据，或取消/不可读时，保留 unknown 和最后可确认观察。观察获得时间与成员变化分开，完整的新响应即使内容相同也不是陈旧观察。

等待期间及阶段边界复用相关漂移和 pending-change 检查；发现冲突停止后续动作，已有副作用按部分失败记录。调用方维持串行窗口，人工检查结论不能替代设备完成证据，也不构成事务隔离。恢复前仍须核清未知后态；超时不证明设备动作已取消。

### 5. 按资源机制取得最小充分证据

| 路径 | 核对范围及不可替代的事实 |
| --- | --- |
| 静态 host/network | 完整 PF 有效成员、IPv4/IPv6 地址语义；集合匹配与本次激活完成分离，读取截断不可通过 |
| port | 相关已加载 PF 规则中端口及范围展开，保留协议、源/目标角色和规则身份；无引用记录 not_applicable，不能用地址表或虚构消费者证明 |
| 静态 networkgroup | 由选中变更与必要现场依赖得到有效集合，再与活动表作地址语义比较；不使用未选中期望值。动态/无法解析成员进入相应能力分支，不当空集合 |
| 动态 Alias | 配置、来源处理/缓存、活动表三层分开；完整读取不等于更新完成，DNS 等内容以设备语义为准，不用执行机自行解析代替设备结果 |
| 禁用/删除 | 区分配置不存在、空表、残留表、活动引用及不可读；只有原生操作要求时检查表消失，不清 PF state，不删除未选择对象 |
| PBR Gateway | 按变化字段和用途核对接口/下一跳、必要路由、已加载消费者中的 route-to 语义及已启用监控配置；不要求默认路由、强制监控、ping 成功或新增消费者 |
| 接口组 | 区分配置保存、接口组注册/成员和 filter reload 完成；有活动规则时核对接口匹配，无引用不伪造规则验证 |
| Filter/NAT/VIP | 保留有依据的同步完成确认，回归既有配置与附加活动检查边界 |

有界分页/大小限制沿用现有读取原则，可按实际接口补必要分页。已知表规模无法完整观察时，plan 列缺口；不把截断当作空表或成功。只对不同核对机制补代表性测试，不做全设备逐对象证明。

### 6. 能力核定与分次交付

实现首先输出一份简短按操作分组的支持说明，基于固定 Collection 和目标 OPNsense 源码/官方接口记录端点、权限、返回语义和限制。不能仅因模块存在就声称具备完成证据。现有 API 无法提供所需事实时，明确哪些动作在写前阻塞；增加只读 SSH、插件、补丁或权限必须单独评估授权，不纳入默认任务。

实施顺序为公共能力准入/候选/等待/结果（AC-01/02/09/10），Alias 的不同核对机制（AC-03–06），再 Gateway/接口组（AC-07/08）。允许分次发布，但每次列明支持范围与仍阻塞的操作；仅完成公共框架或记录缺口不能把尚未实现的资源任务勾选完成。

## Risks / Trade-offs

- 静态 Alias 过去凭表匹配可完成，修正后某些动作会被写前阻塞 → 作为保护收紧明确公告，提供缺口和新计划路径，不保留静默旧模式。
- 现有 API 可能缺少动作完成、缓存来源或注册信息 → 不预承诺全部类型可用；交付能力边界，额外通道另行授权。
- 缓存/动态内容在 plan 后变化 → apply 复核允许复用条件，不能自动扩大已审查动作；不要求固定动态成员快照。
- 共享 reload 会影响未选中待应用修改 → 保留绑定检查、串行窗口和阶段冲突停止，不声称对象级激活隔离。
- 更严格合同与旧产物不兼容 → 版本化并要求重做 plan；旧恢复材料仅用于可表达的配置逆向，不追认旧动作证据。

## Migration Plan

先完成能力核定和格式合同测试，再实现公共路径和各类适配；按计划范围更新通用手册、合成示例及软件测试结果。调用方后续固定匹配的 launcher/runtime 并重做候选，维护成功范围和未验证项；iaas 不改调用方 inventory、部署指针或生成器基线。

本次只创建设计。实施前按仓库规则确认对应实现分支和工作树，未经确认不自动切换。发布与真实设备代表性验证均不在本次操作范围；恢复设备仍走已有显式新候选流程，不因软件回退自动回滚。
