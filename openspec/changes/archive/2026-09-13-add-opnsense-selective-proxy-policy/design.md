## Context

动机见 [proposal.md](proposal.md)。既有运行时验证并序列化 aliases、vips、gateways、filter-rules；底层 Ansible 已提供资源写入与激活。主规则 spec 仍要求手写输入，当前未提交实现则增加了专用策略编译器与运行时分支；后者不符合本次确认的仓库边界。

本轮仅调整规划。当前代码尚未按新边界整理，旧测试结论不能证明修订后合同完成，见 [implementation-status.md](implementation-status.md)。

## Goals / Non-Goals

**Goals:** 用同一标准资源合同接收手写或生成声明；修正实际遇到的原生约束与已有通用安全校验；保持直接 Ansible 与离线入口的校验一致。

**Non-Goals:** 高层分流输入、FakeIP/国内列表分类、直连/代理例外冲突、来源展开、环境基础配置组合、迁移批次生成、现场 ACL 推导、部署授权、网关共享开关的自动修改，以及任何下一跳之后的管理。不建设通用策略引擎、事务/自动回滚平台或新发布体系。

## Decisions

### 1. 来源中立的标准资源合同

调用方先生成 iaas 已支持的低层 Alias/Rules 文件，再交给既有校验/执行入口。规则继续使用 `opnsense_filter_rules`、scope/slug 身份和显式状态；Alias 继续使用 `opnsense_aliases` 及现有名字、类型和状态合同。两者的手写和生成文件适用同一套通用校验，不要求生成器在 iaas 内实现或注册。Gateway/VIP 本次继续引用既有基础源文件，保持其来源与执行合同，不要求调用方生成副本。

将主规则 requirement 名称由 Hand-written filter rule desired state 调整为 Caller-authored filter rule desired state，同时将 Hand-written alias desired state 调整为 Caller-authored alias desired state，允许从调用方维护的源确定性派生。同步主 specs 时将 Alias 的 Purpose 中手写限定改为调用方维护的期望状态；本轮只提供 delta，不直接修改主 specs。设备导出可供调用方审查，但不能未经整理直接成为部署源。用普通生成别名及规则样例验证通用接入，不以分流业务作为准入条件。

替代方案是在运行时保留专用 policy 分支；不采用，因为它要求 iaas 理解调用方策略。也不以任意脚本执行接口绕过标准资源合同。

### 2. 通用约束与通用保护分开

原生/固定依赖约束与 iaas 自身的管理访问保护分别说明。反向 source/destination 只能使用一个目标；多个地址可以通过合法的单一别名目标表达，但不能将多目标反向列表传到设备。该规则与代理业务无关。

已有入口自身网络保护保留。增加可选的 `opnsense_filter_rule_context`，只包含 `interface_networks`（接口到 CIDR 数组）与 `aliases`（标准别名声明数组）。无上下文调用继续执行已有保守校验；上下文不提供跳过校验或宣称“安全”的布尔值。

对反向 deny，校验器可沿静态 host/network/networkgroup 地址成员证明：排除的单一目标覆盖该规则地址族内声明的入口网络。动态 URL Table、域名解析和未知成员不提供静态覆盖证据；若其余静态成员已经足够覆盖，可以基于这些成员通过，否则不放行原会被保护拒绝的规则。inet/inet6/inet46 按实际规则地址族检查，不以仅有 IPv4 证据推断 IPv6 安全。

上下文来自调用方所选基础声明/已核对事实；生成器输出派生副本，不形成第二份手工源。组合入口同时收到上下文和对应别名时检查声明一致。上下文只证明给定声明之间的关系，不证明设备现状，不能自动扩大已有保护范围或要求整台设备全量纳管。

### 3. 保持已有引用和增量管理语义

复用资源身份检查、别名局部依赖与既有在线解析流程。未知外部引用不同于本地缺失/非法引用：保留现有合同，不将所有本地未声明对象一律判为不存在，不新增全设备闭合对象图门禁。

基础配置与专用增量由调用方组合。iaas 管理收到的显式对象，不根据文件省略、空输入或命名空间推断删除，也不推断旧策略迁移。数值顺序不能证明现场 floating/group/system 规则和 ACL 的实际优先级。

### 4. 校验与运行时交接

调用方使用受支持的离线命令/运行时接口校验，不导入私有 Python 模块。校验拒绝发生在凭据和设备写入之前；Ansible 加载值后的必要复验同样位于凭据前，避免两个入口判定不一致。

Ansible 带元数据的值若保持合法基础类型，应在适配边界规范化；不得全局放松严格类型检查、把字符串转为布尔/整数，或把 bool 当作整数接受。以真实 Ansible 模板加载路径验证该差异，不能仅调用 Python 函数替代。

保留低层 check/generate 与现有 Ansible 管理入口，不为命令菜单完整性增加 launcher apply。资源保存、激活失败及恢复仍按现有合同报告；不承诺跨资源事务。分流保护阶段、共享网关设置影响与状态清理由 infra-ops 编排，受支持的人工设置路径不要求上游自动化实现。

### 5. 移出专用实现，维持单向依赖

后续代码调整先与 infra-ops 确认专用逻辑和测试承接，再从 iaas 移出 `opnsense_policy.py`、分流 fixtures/文档以及运行时专用分支。iaas 不反向依赖 infra-ops。通用校验测试改用普通防火墙声明，不以分流生成器存在作为测试前提。

只提取本次确有通用语义的最小改动，不机械迁移所有新校验。分类基线、例外冲突、来源与端口展开、迁移配置生成均留在调用方。未发布的专用输入不作为需要长期兼容的正式接口。

## Risks / Trade-offs

- [通用入口调用面较广] → 后续代码编辑前刷新 GitNexus 影响分析，运行相关 OPNsense 与运行时回归；本轮旧索引返回 CRITICAL 且提示落后 3 个提交，不用它证明当前完整覆盖。
- [上下文陈旧或与所选声明不一致] → 检查可知冲突，声明离线证明范围；现场事实仍由调用方在部署前复核。
- [Python 与 Ansible 值类型不同] → 在适配边界处理并通过真实本地 Ansible 加载测试，不削弱领域类型规则。
- [专用实现迁出后出现双份维护] → 两仓 change 以标准资源接口交接，承接完成后 iaas 移除专用分支，不保留复制实现。
- [保存成功但激活失败] → 复用已有明确结果与恢复入口，不增加事务保证。

## Migration Plan

1. 保留两仓当前未提交内容；本轮文档修改不触发代码移动、回滚或部署。
2. 后续实现先检查分支与工作树，按用户规则办理必要切换；由 infra-ops 承接专用生成器，iaas 收敛实现与测试。
3. 补齐通用输入、反向匹配、上下文及 Ansible 适配，运行代表性正反例和现有兼容回归。
4. 更新通用操作文档，记录调用方生成文件的标准接入方式；删除或改写仍宣称 iaas 提供分流编译的说明。
5. 按既有发布流程提供必要的通用修正版本；没有发布或镜像验证时如实记录。infra-ops 自行固定兼容版本并执行自己的生成、审查、部署与验收，不把两仓任务互相标为完成。
