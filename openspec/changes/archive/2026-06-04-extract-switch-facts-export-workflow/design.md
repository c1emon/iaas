## Context

The SKS8300 read-only facts workflow now has a clean profile-driven collection pipeline, but the role still owns local file persistence. That makes `switch_readonly_facts` both a provider of facts and a consumer that decides export paths, formats, raw file behavior, and README content.

For a facts role, file writing is a side effect that callers may not want. Some callers may only want in-memory facts for assertions, templating, or later configuration workflows. The playbook entrypoint can still provide the current export experience, but export should be a separate consumer workflow layered after collection and parsing.

## Goals / Non-Goals

**Goals:**

- Make `switch_readonly_facts` stop writing files by default.
- Keep the role responsible for validation, profile planning, collection, parsing, and producing export-plan variables.
- Move structured and raw output file writing into a playbook-level export task file or equivalent caller-owned workflow.
- Preserve the existing `playbooks/switches/readonly-facts.yml` operator experience when export is enabled by that playbook.
- Preserve structured facts schema, raw output filenames, redaction behavior, and command-level raw export policy.

**Non-Goals:**

- Do not add switch configuration mutation.
- Do not introduce a new published Ansible collection or custom module.
- Do not change SKS8300 parser behavior or fact schema.
- Do not remove the ability to write repository exports from the switch playbook.
- Do not make raw plaintext running configuration exportable.

## Decisions

### Keep the facts role as a provider only

`switch_readonly_facts` should end after `parse.yml`. It should expose variables such as:

- `switch_facts`
- `switch_command_outputs`
- `switch_raw_export_items`
- `switch_read_command_plan`
- `switch_cli_command_results` / raw outputs as needed for diagnostics

This makes the role usable by playbooks that want facts without local persistence.

Alternative considered: keep a role variable such as `switch_export_enabled` and skip export by default. Rejected because export path/format variables would remain role API, preserving the mixed responsibility that this change is intended to remove.

### Move file persistence to playbook-local export tasks

The current `export.yml` logic should move to a playbook-local task file such as `playbooks/switches/tasks/export-readonly-facts.yml`. The switch playbook can import it after the role when it wants repository artifacts.

This keeps the operator-facing switch playbook useful while making persistence visibly caller-owned.

Alternative considered: create a reusable `switch_facts_export` role immediately. Rejected for now because there is only one known consumer. A role can be introduced later if multiple playbooks need the same export workflow.

### Keep raw export policy generated by the profile

The SKS8300 profile should still decide which command outputs are eligible for raw export and whether they require redaction. The file-writing workflow should consume `switch_raw_export_items`; it should not reimplement sensitivity decisions.

Alternative considered: move raw export policy entirely into the export task file. Rejected because sensitivity and raw-export rules belong to the platform profile command catalog, not to a generic filesystem writer.

### Move export defaults out of the facts role

Variables such as `switch_export_formats`, `switch_export_save_raw`, `switch_export_dir`, and `switch_raw_output_dir` should be defined by the playbook/export workflow. They should no longer be defaults of `switch_readonly_facts`.

Alternative considered: leave defaults in the role for compatibility. Rejected because the proposal intentionally makes this a breaking API cleanup.

## Risks / Trade-offs

- Breaking callers that relied on the role writing files → Document migration: run the switch playbook export task or define equivalent caller-side copy tasks.
- Export task file can still look tightly coupled to role variables → Treat role output variables as the contract and document them clearly.
- Raw export redaction could regress when moving tasks → Keep `switch_raw_export_items` produced by the profile and validate generated `show-running-config.txt` remains redacted.
- Existing playbook output could change paths or filenames → Preserve current export variable names and file layout at playbook/export-task scope.

## Migration Plan

1. Remove `export.yml` import from `roles/switch_readonly_facts/tasks/main.yml`.
2. Move or copy export tasks into `playbooks/switches/tasks/export-readonly-facts.yml`.
3. Define export variables in `playbooks/switches/readonly-facts.yml` or playbook-local vars.
4. Update role README to list output variables rather than file artifacts.
5. Update switch playbook README to show optional export workflow usage.
6. Run syntax, lint, Python validation, and live `sw-core` export validation.

Rollback is to restore the role export phase and role defaults. Because this change remains read-only, rollback does not require switch configuration changes.

## Open Questions

- Should the playbook always import the export task by default, preserving current CLI behavior, or should export require an explicit variable? Initial implementation should favor preserving the existing playbook behavior while keeping the role itself side-effect free.
