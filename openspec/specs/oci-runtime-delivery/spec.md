# oci-runtime-delivery Specification

## Purpose
Define reusable OCI runtime delivery and its caller contract.

## Requirements

### Requirement: Runtime operates independently of the source checkout
The system SHALL publish one `linux/amd64` OCI runtime containing the reusable
implementation, Ansible resources, OpenTofu modules and locked execution tools
required by its documented operations.

#### Scenario: Run the image without a source checkout
- **WHEN** an operator starts the image with external synthetic inputs and an explicit offline operation
- **THEN** the operation SHALL use implementation and resources supplied by the image
- **AND** it SHALL NOT require the source checkout, developer virtual environment, or an implicit environment directory
- **AND** startup and offline operations SHALL NOT download or install dependencies

#### Scenario: Invoke without an operation
- **WHEN** the image is started without an operation
- **THEN** it SHALL display usage without generation, secret resolution, online access, or infrastructure mutation

#### Scenario: Inspect release contents
- **WHEN** the runtime is built for publication
- **THEN** execution dependencies SHALL have committed exact version or digest selections, using existing standard lockfiles where applicable
- **AND** every image layer SHALL exclude real environment configuration, credentials, kubeconfig, state, plans, Git history, developer environments and runtime caches
- **AND** required upstream license notices SHALL be retained

#### Scenario: Publish only runtime necessities
- **WHEN** the final runtime image is assembled
- **THEN** its layers SHALL contain only resources and dependencies required by the supported execution interface, plus required license notices and runtime metadata
- **AND** they SHALL NOT contain repository documentation, README files, OpenSpec, tests/fixtures, examples, review reports, agent instructions, CI/editor configuration, build recipes or build-only tools
- **AND** build and test stages SHALL NOT cause those excluded files to be copied into the published image
- **AND** removing non-runtime content SHALL preserve executable templates, plugin metadata and the supported generation/validation operations
- **AND** documentation generated by an explicitly requested runtime operation SHALL be written to the caller's output location rather than baked into the image

#### Scenario: Rebuild after a repository code-only change
- **WHEN** implementation source changes while dependency pins, locks and installation rules remain unchanged and the builder cache is available
- **THEN** dependency installation steps SHALL reuse their build cache
- **AND** the final image SHALL retain separate dependency and repository-content layers, preserving the dependency layer for that rebuild
- **AND** changes to dependency locks or installation rules MAY invalidate the corresponding dependency cache

### Requirement: Credential acquisition belongs to the caller
The runtime SHALL accept resolved credentials through documented environment
variables or explicitly supplied protected files, independently of their source.
It SHALL NOT authenticate to 1Password, resolve secret references, invoke or ship
the 1Password CLI, or require `OP_SERVICE_ACCOUNT_TOKEN`.

#### Scenario: Caller injects credentials from 1Password
- **WHEN** a caller chooses 1Password for a credentialed operation
- **THEN** the caller SHALL own authentication, reference resolution and injection before invoking IaaS
- **AND** a CI caller SHALL own its noninteractive service identity and bootstrap token
- **AND** the IaaS container SHALL receive only the required operation credentials, not a 1Password service token or desktop session

#### Scenario: Caller injects traditional Secrets
- **WHEN** a caller supplies equivalent credentials using CI Secrets, host environment variables or protected Secret file mounts
- **THEN** the same operation SHALL accept them without a 1Password account, binary, login or provider selector
- **AND** existing sensitive-file owner/mode checks and SSH host-key verification SHALL remain enforced for both input routes

#### Scenario: Required credentials are missing
- **WHEN** an operation requiring credentials lacks a required resolved value or protected file
- **THEN** it SHALL fail before the credentialed operation with an actionable error that does not expose secret values
- **AND** it SHALL NOT retrieve a secret from a provider or silently fall back to another source

#### Scenario: Offline execution has no secret provider
- **WHEN** offline generation, validation or image smoke checks run without `op`, provider tokens or infrastructure credentials
- **THEN** they SHALL succeed for valid non-secret inputs without resolving reference metadata
- **AND** credential values SHALL NOT be embedded in images, committed artifacts, command-line values or logs

### Requirement: Runtime paths are environment-neutral
The system SHALL provide explicit generic environment and output directory
selection for both local checkout and container execution, with no implicit
Astra selection or environment-specific runtime naming.

#### Scenario: Select another environment
- **WHEN** an operator supplies `ENVIRONMENT_DIR` and `OUTPUT_DIR` for a valid independently supplied environment
- **THEN** supported operations SHALL use that environment's authored data and the selected output location
- **AND** Ansible inventory, domain variable files, generated source descriptions, helper command paths and execution variables SHALL NOT select or describe an unrelated selected environment
- **AND** common generated data schemas, scope checks and infrastructure safety limits SHALL remain unchanged

#### Scenario: Inputs are missing or legacy selectors are supplied
- **WHEN** an environment operation lacks its required explicit directory/file inputs or supplies a removed environment-specific execution variable
- **THEN** it SHALL fail with an actionable input or migration message before generation, online access, or mutation
- **AND** it SHALL NOT fall back to `environments/astra` or silently ignore the removed variable
- **AND** environment-independent help, tests and build commands SHALL NOT require unused environment inputs

#### Scenario: Run with separate input and output mounts
- **WHEN** an offline generator runs with read-only authored inputs and an external writable output root from an arbitrary working directory
- **THEN** it SHALL write non-sensitive generated data beneath `OUTPUT_DIR/generated` by default, or to an explicitly selected generated-only directory/file, and runtime work beneath `OUTPUT_DIR/runtime`
- **AND** it SHALL NOT overwrite authored inputs or image-local implementation resources
- **AND** the supported caller UID/GID invocation SHALL produce usable outputs while preserving existing sensitive-file ownership and mode checks

#### Scenario: Output placement is unsafe
- **WHEN** selected output paths overlap authored inputs or resolve into implementation resources
- **THEN** the command SHALL reject the paths before writing

#### Scenario: Host helper command names change
- **WHEN** a maintainer prepares existing PVE hosts to use generic helper names
- **THEN** the documented cutover SHALL retain the audited argument, identity, sudo and locking protections
- **AND** it SHALL prevent old and new helper paths from operating concurrently under independent locks
- **AND** packaging validation SHALL NOT be reported as completed host installation or live cutover

### Requirement: External OpenTofu roots can resolve versioned modules
The runtime SHALL expose its delivered OpenTofu modules at a documented stable
image-local path, independently of the environment repository's physical layout.

#### Scenario: Validate an externally owned root
- **WHEN** a synthetic external root references the documented module path and supplies a committed provider lock
- **THEN** backend-disabled init and validation SHALL resolve the module delivered in the selected image without a source checkout
- **AND** initialization SHALL NOT silently upgrade the provider lock
- **AND** the check SHALL NOT access infrastructure or operate on live state

#### Scenario: Use runtime tools in a private deployment workflow
- **WHEN** an external workflow uses the image's OpenTofu tools
- **THEN** the external workflow SHALL own the working root, backend, lockfile, plan/state storage and deployment authorization
- **AND** the runtime SHALL NOT bake these into the image, migrate state, or silently treat ephemeral container-local state as a configured persistent backend

### Requirement: Release publication selects and tests the exact source revision
The repository SHALL publish a versioned runtime through GitHub Actions when a
GitHub Release is published, using the release's tagged commit as the source.

#### Scenario: Publish a stable or prerelease version
- **WHEN** a Release is published with a supported `vX.Y.Z` or `vX.Y.Z-<suffix>` tag
- **THEN** the workflow SHALL validate and build that exact tagged revision
- **AND** repository offline checks, secret scanning and container smoke checks SHALL pass before pushing the tested image artifact
- **AND** the image SHALL be tagged with the release version under `ghcr.io/<lowercase repository owner>/iaas-runtime`
- **AND** the published artifact SHALL preserve the tested image config and layers rather than being rebuilt after testing

#### Scenario: An event is not a supported publication
- **WHEN** a PR, main-branch push, tag-only push, draft creation or release-body edit occurs
- **THEN** it SHALL NOT publish a release image
- **AND** an invalid release version SHALL be rejected before publication

#### Scenario: A validation or build fails
- **WHEN** a required pre-publication check or image build fails
- **THEN** the workflow SHALL fail without publishing that candidate
- **AND** it SHALL NOT claim a usable runtime solely because the GitHub Release exists

### Requirement: Publication credentials are separate from infrastructure access
The publication workflow SHALL use the ephemeral repository `GITHUB_TOKEN` for
GHCR writes and SHALL NOT require infrastructure credentials or internal routes.

#### Scenario: Build and publish jobs run
- **WHEN** a release workflow builds, tests and publishes
- **THEN** build/test jobs SHALL have no package-write permission
- **AND** only the dependent publish job SHALL receive package-write permission
- **AND** no job SHALL require a developer's interactive 1Password session or perform infrastructure planning, deployment, or external platform triggering
- **AND** tokens and runtime credential material SHALL NOT appear in logs or image contents

### Requirement: Consumers receive a verified immutable image reference
The publication workflow SHALL report a registry digest, version and source
revision, and verify public consumption before reporting distribution success.

#### Scenario: Publish and pull by digest
- **WHEN** an image has been pushed
- **THEN** CI SHALL record its canonical digest reference with the release tag and source commit
- **AND** a clean unauthenticated consumer SHALL pull that digest and run a minimal invocation
- **AND** documentation SHALL direct private repositories to pin that digest instead of a mutable tag

#### Scenario: Public visibility or pull verification fails
- **WHEN** a push succeeds but anonymous digest consumption fails
- **THEN** distribution acceptance SHALL remain failed or incomplete
- **AND** the report SHALL distinguish the existing pushed artifact from successful public distribution and describe retry/visibility setup

#### Scenario: Rerun an existing version
- **WHEN** a release publication is retried and its image tag already exists
- **THEN** the workflow SHALL NOT overwrite the existing version
- **AND** it SHALL verify the existing source revision and recheck consumption of its existing digest
- **AND** a conflicting source revision SHALL fail and require a new version
- **AND** competing publication jobs for the same version SHALL be serialized

### Requirement: Acceptance remains bounded to runtime delivery
The repository SHALL validate representative synthetic container workflows and
separately report real registry delivery evidence without claiming infrastructure
or platform qualification.

#### Scenario: Exercise packaged automation
- **WHEN** container acceptance runs without infrastructure credentials
- **THEN** it SHALL cover grouped inventory generation/freshness, K3s composition/rendering and Ansible resource/plugin discovery with container networking disabled
- **AND** it SHALL cover invalid input, stale output and directory boundary failures
- **AND** a separate backend-disabled OpenTofu check SHALL cover packaged module/provider compatibility with only dependency downloads permitted
- **AND** image-content checks SHALL confirm excluded data classes using representative fixtures and standard tooling

#### Scenario: Record completion evidence
- **WHEN** maintainers review delivery completion
- **THEN** local/PR smoke results SHALL prove only software behavior
- **AND** actual Release workflow and digest-pull results SHALL be required to claim GHCR delivery
- **AND** Forgejo deployment, state locking, real VM/K3s operations, handoff correctness and platform bootstrap SHALL remain later-stage acceptance

### Requirement: Repair-first implementation gate
This change SHALL complete and validate existing-runtime repairs before dependency upgrades or new OPNsense capability implementation.

#### Scenario: A prerequisite repair remains incomplete
- **WHEN** any repair task 0.1–0.14 or the repair gate 0.15 is incomplete
- **THEN** tasks 1–5 SHALL remain blocked from implementation
- **AND** design or audit test results SHALL NOT be treated as completed repair evidence

#### Scenario: Repair phase is accepted
- **WHEN** targeted regressions, affected Ansible checks, the existing offline gate and final-image smoke pass
- **THEN** actual software evidence SHALL be recorded separately before beginning the reviewed dependency refresh
- **AND** no live infrastructure qualification, release publication or destructive recovery SHALL be implied

### Requirement: Working-directory independent lifecycle entrypoints
The OCI and checkout entrypoints SHALL resolve their own Makefile and nested targets without requiring the caller to run from the implementation directory.

#### Scenario: A lifecycle command runs from an external working directory
- **WHEN** the caller invokes PVE plan, apply or destroy through the shipped entrypoint
- **THEN** recursive commands SHALL use the explicitly selected implementation Makefile
- **AND** the caller's directory SHALL remain available for its own files without becoming the implicit implementation root

### Requirement: CI validates the shipped execution baseline
The main checkout gate SHALL use the shipped OpenTofu version and explicitly installed Collection baseline, with realistic representative operation-state regressions.

#### Scenario: Main CI installs infrastructure tools
- **WHEN** the gate prepares its toolchain
- **THEN** it SHALL use coordinated fixed versions rather than latest OpenTofu or unpinned shared Collections
- **AND** the existing source-versus-dependency image layering SHALL remain intact

#### Scenario: Repaired orchestration is validated
- **WHEN** regression tests exercise lifecycle entrypoints
- **THEN** safe substitutes SHALL run through actual orchestration for installed, partial, failed-activation and arbitrary-directory states
- **AND** constant all-success synthetic facts alone SHALL NOT satisfy that coverage

### Requirement: Coordinated execution dependency updates
Runtime dependency updates SHALL keep the developer environment and OCI image compatible and reproducible without expanding a focused capability change into an unrelated toolchain refresh.

#### Scenario: The Ansible distribution requires a newer core patch
- **WHEN** this change upgrades the reviewed Ansible distribution to 14.4.0
- **THEN** the runtime core pin and uv lock SHALL be updated together to the reviewed 2.21.4 baseline
- **AND** explicitly installed shared Collections SHALL be aligned between developer and image manifests using the reviewed candidate versions
- **AND** oxlorg.opnsense SHALL remain pinned to 26.1.11 unless a separately evidenced compatibility requirement changes that decision

#### Scenario: Dependency inputs change
- **WHEN** the Python or Collection dependency pins are updated
- **THEN** the final runtime image SHALL be rebuilt with the updated dependency layer and pass relevant existing runtime smoke checks and synthetic validation
- **AND** dependency resolution alone SHALL NOT be reported as image or appliance compatibility
- **AND** subsequent repository-source edits SHALL preserve separation from dependency installation layers

#### Scenario: The focused refresh is accepted
- **WHEN** the reviewed dependency upgrade passes software validation
- **THEN** its versions and evidence SHALL be recorded separately from new OPNsense functionality
- **AND** unrelated providers, base images and tools SHALL NOT be upgraded implicitly
- **AND** neither real-appliance changes nor image publication SHALL be implied

### Requirement: Launcher delivery and compatibility metadata
Runtime delivery SHALL include a separately installable versioned launcher and a documented compatibility contract without adding host toolchains to ordinary runtime prerequisites.

#### Scenario: Install or upgrade a launcher
- **WHEN** a caller installs or explicitly upgrades the launcher
- **THEN** project-owned instructions SHALL provide supported host artifacts, standard checksums, prerequisites and compatibility guidance
- **AND** caller image/configuration selections SHALL NOT be silently changed
- **AND** runtime execution SHALL NOT auto-update the launcher

#### Scenario: Assemble the adapted image
- **WHEN** the adapted runtime image is built
- **THEN** it SHALL contain the new runtime parser/dispatcher and necessary compatibility metadata while preserving existing runtime-only content and dependency layering rules
- **AND** real caller configuration, backend values, plans and credentials SHALL remain excluded

### Requirement: Explicit platform capability
The runtime SHALL support Linux amd64 and documented Apple Silicon local use with explicit container-platform selection, and SHALL publish the evaluated scope of native Linux arm64 support.

#### Scenario: Build a native ARM64 image
- **WHEN** a caller selects `RUNTIME_PLATFORM=linux/arm64` for the image build
- **THEN** the build SHALL use pinned ARM64 tools and their checksums, and CI SHALL build and check AMD64 and ARM64 serially
- **AND** launcher admission SHALL match the requested platform against the running image architecture
- **AND** saved plans SHALL bind that architecture and reject cross-architecture reuse before infrastructure writes
- **AND** software build validation SHALL NOT imply real-facility qualification

#### Scenario: Publish one version for both architectures
- **WHEN** a published Release triggers image distribution
- **THEN** both native architectures SHALL be built and tested serially before the publication job is admitted
- **AND** image CI jobs SHALL use the same pinned Docker CLI/Engine baseline supporting platform-specific image inspection, with consistent image storage and daemon selection across temporary authentication directories
- **AND** publication SHALL load those tested artifacts without rebuilding, check their source labels and platform identities, and publish a version manifest containing exactly Linux AMD64 and ARM64
- **AND** existing version and architecture tags SHALL NOT be overwritten; only the same tested artifacts may resume a partial or completed publication
- **AND** anonymous consumption SHALL pull the shared manifest digest and execute the expected platform on both architectures
- **AND** historical single-platform tags SHALL remain unchanged

#### Scenario: Inject publication credentials in CI
- **WHEN** CI publishes image or launcher assets
- **THEN** publication credentials SHALL be explicitly supplied by the CI platform
- **AND** publication SHALL run noninteractively without obtaining credentials from local 1Password or developer shell startup files

#### Scenario: Run on Apple Silicon
- **WHEN** a caller selects a supported Apple Silicon launcher and Linux amd64 container mode
- **THEN** documentation and startup checks SHALL identify the required container-engine emulation capability and operation limitations
- **AND** incompatible engine/platform combinations SHALL fail rather than silently selecting another platform

#### Scenario: Evaluate native arm64
- **WHEN** native Linux arm64 support is assessed
- **THEN** the result SHALL identify supported and unsupported operations from actual tool/provider compatibility evidence
- **AND** unsupported combinations SHALL be rejected or require an explicitly selected amd64 alternative
- **AND** unexecuted platforms SHALL NOT be labeled validated

### Requirement: Bounded runtime adaptation acceptance
Acceptance SHALL use grouped representative workflows and distinguish software validation from actual platform/daemon/S3 service validation.

#### Scenario: Run software checks
- **WHEN** the adaptation is validated with synthetic inputs
- **THEN** grouped checks SHALL cover offline operation, path/reference failures, component scope, version compatibility, permissions, saved plans and recovery retention
- **AND** tests SHALL exercise phase failures without real infrastructure mutations or live credentials

#### Scenario: Validate actual execution modes
- **WHEN** local Docker, Apple Silicon, Forgejo DinD or a selected S3-compatible service is reported as accepted
- **THEN** that execution mode SHALL have actual evidence from a separately identified and authorized bounded environment
- **AND** mocks, another platform or simple S3 upload/download SHALL NOT substitute for the claimed mode's path/permission or native-lock behavior
- **AND** absent evidence SHALL remain explicitly pending without triggering shared-environment access automatically

### Requirement: Canonical adaptation guidance
The IaaS repository SHALL own installation, operation, migration and troubleshooting guidance; callers SHALL own environment values, backend selection, credentials and authorization.

#### Scenario: Adopt the new interface
- **WHEN** a caller follows migration guidance
- **THEN** it SHALL describe component configuration, runtime selection, local/DinD execution, S3 state and saved-plan/recovery outputs
- **AND** it SHALL preserve existing explicit entrypoints or give clear versioned errors without rewriting sources or migrating state
- **AND** it SHALL distinguish serial workflow assumptions and deferred concurrency alternatives from implemented guarantees
