# IaaS Runtime 配置与本地执行适配需求清单

日期：2026-09-11。
状态：已在 [OpenSpec change：adapt-runtime-config-and-local-execution](../openspec/changes/adapt-runtime-config-and-local-execution/proposal.md) 的实现分支完成代码与本地合成验收；实际平台边界见[验收记录](runtime-adaptation-validation.md)。尚未发布新镜像或启动器。
归属：本文由 `iaas` 仓库维护，作为实现与验收依据，不作为 `infra-ops` 的长期实现计划。

## 目标与范围

本轮同时解决环境配置组织、重复事实维护，以及本地和 CI 调用运行时的问题。
用户应能在本地完成不依赖实际环境的检查和生成，无需每次通过 CI。
本地和 CI 消费相同的环境配置与运行时版本，在线操作保留明确的目标、凭据和授权边界。

本清单仅针对 `iaas-runtime` 的改造与适配，不包含真实环境部署。
具体配置及命令接口见[启动器指南](runtime-launcher.md)。

## 1. 环境配置接口

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| ENV-01 | 通过一个环境入口文件定位各组件配置，解除对 `inventory/`、`ansible/vars/` 等调用方固定目录的依赖 | 同一套运行时能够读取不同目录布局的环境配置 |
| ENV-02 | 支持按 OPNsense、交换机、PVE、基础服务、K3s 等设施组织输入 | 调用方无需按照运行时内部 Ansible 目录维护配置 |
| ENV-03 | 明确共享事实与组件策略的边界，支持设备、地址、网段等必要引用 | 同一事实可维护一次；引用缺失、类型不符或循环引用时明确报错 |
| ENV-04 | 不将语义不同但当前值相同的字段强制合并 | 管理地址、健康探针目标、网关地址等可以分别声明 |
| ENV-05 | 支持显式选择场景，分离日常配置、E2E 和测试输入 | 未选择的场景不参与生成或执行；测试场景不会覆盖默认环境输入 |
| ENV-06 | 支持只校验、生成或执行指定组件，并检查其必要依赖 | OPNsense 操作不要求准备无关的 PVE、K3s 配置；依赖检查可读取必要配置，但不得自动执行依赖组件或扩大设备变更范围 |
| ENV-07 | 对旧配置提供明确迁移说明和版本边界 | 旧格式得到明确支持或清晰迁移错误，不静默改变含义；不自动改写调用方源文件 |
| ENV-08 | 明确配置路径解析与源文件保护契约 | 相对路径以声明它的配置文件所在目录为基准，不依赖调用工作目录；所有实际引用的源文件均纳入输出覆盖保护 |

引用机制只覆盖当前明确需要的能力，不引入任意脚本执行、复杂多层继承或通用模板语言。
环境入口以外的文件必须通过配置引用或显式参数声明；符号链接按解析后的实际位置进行边界检查。
本地 Docker 与 DinD 传递输入时必须保留引用关系，外部文件不可用或无法安全映射时明确报错，不猜测替代路径。

## 2. 本地与 CI 统一入口

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| RUN-01 | 提供由 `iaas` 维护的轻量启动器，封装镜像选择、挂载、用户和运行参数 | 用户无需每次手写完整 `docker run` |
| RUN-02 | 本地和 CI 使用相同的环境输入与操作入口 | 同一版本、同一输入在两种执行方式下具有一致语义 |
| RUN-03 | 集中读取调用方指定的运行时版本，支持固定 digest | 不隐式使用 `latest`，本地与 CI 不各自维护一套版本 |
| RUN-04 | 明确区分本地 Docker 与现有 Forgejo DinD 执行方式 | 两种方式均能正确传递输入、输出和受保护文件，不假设客户端路径一定存在于 daemon 主机 |
| RUN-05 | 自动准备独立任务目录、可写临时目录及适当文件权限 | 不污染源配置目录；本地结果可由调用用户读取和清理 |
| RUN-06 | 正确传播退出码、取消与中断，并清理任务自有临时资源 | 失败不被包装成成功，不清理其他任务或共享资源；清理须保留 DATA-07 规定的恢复产物，保留失败时停止相关清理 |
| RUN-07 | 降低本机依赖要求 | 普通使用者无需在宿主机安装完整 Python、Ansible、OpenTofu 工具链；启动器依赖有明确说明 |
| RUN-08 | 明确配置格式、启动器接口与运行时镜像的版本兼容范围 | 使用简单版本字段和兼容说明；本地与 CI 均在生成或在线操作前检查兼容性，不支持的组合明确失败，不静默降级或改用其他镜像 |

## 3. 离线与在线操作分级

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| OPS-01 | 提供纯本地检查：语法、schema、引用、关键不变量与组件组合关系 | 镜像准备好后，可断网执行，不读取设施凭据、不访问设备 |
| OPS-02 | 提供无设施副作用的生成入口 | 只读取所选输入并写入指定输出目录，不修改源文件 |
| OPS-03 | 将依赖下载与纯离线检查分开 | provider 初始化等网络需求明确可见，不在离线检查中自动安装依赖 |
| OPS-04 | 区分配置检查、设备只读诊断、在线计划与实际变更 | 帮助信息和执行结果明确说明是否联网、是否读 state、是否有写入副作用 |
| OPS-05 | 保留组件自身操作差异 | 不将 Ansible check mode、OpenTofu plan 或设备 API 校验误报为具有相同保证的通用计划 |
| OPS-06 | 在线操作显式选择目标和范围 | 不默认操作所有设备，不因缺少参数或依赖关系扩大执行范围；操作要求完整集群时，拒绝不完整选择并说明原因，由调用方重新显式选择 |
| OPS-07 | 支持保存 OpenTofu 计划并应用调用方指定的计划文件 | 应用的是指定的原生计划文件，不重新规划或回退到按当前配置直接 apply；计划失效或不匹配时明确失败 |
| OPS-08 | 当前阶段复用调用方已有的单任务串行 CI 执行约定 | 同一环境的完整变更流程（含 snippets 上传和 apply）串行执行；调用方避免本地变更与 CI 部署或其他本地变更重叠，运行时不宣称已提供跨入口的完整流程互斥 |

已实现的命令及组件差异见[启动器操作表](runtime-launcher.md#select-inputs-and-an-operation)；指定计划通过 `apply-saved-plan` 应用。
镜像首次拉取需要网络；本清单中的断网执行指镜像准备完成后的纯检查和生成。
首轮各组件必须支持的操作及既有独立入口边界，以 [设计中的组件支持表](../openspec/changes/adapt-runtime-config-and-local-execution/design.md#5-操作分级与凭据)为准；帮助和分组分发测试须覆盖该表，不能仅以“未支持的组合报错”替代组件支持承诺。

### 已确定能力：保存并应用指定计划

- OpenTofu 计划输出包含可应用的原生计划文件及供审阅的内容；普通日志仅输出非敏感摘要，完整计划和审阅内容按 DATA-03 作为敏感产物处理。
- 调用方显式选择保存位置和待应用计划；计划及执行所需的配套产物须能跨本地、CI 和独立任务目录传递，不随规划任务临时目录清理而丢失。
- 计划关联所选环境、root、backend/workspace、场景、范围、输入来源、镜像 digest 和 provider 锁文件；优先复用原生计划、锁文件及 DATA-06 的简明摘要，不另建证据系统。应用前核对目标和执行版本一致，并保留 OpenTofu 自身的 state 过期检查与锁机制。
- 原生计划成功生成后，在配套 manifest 中记录其 `plan_sha256`，与既有 tfvars/snippets 摘要一同保存。应用前校验所选计划与记录值，缺失或不匹配在任何 SSH 写入前失败；应用时不得补写或重新绑定期望值。该最小绑定用于阻止同一环境内计划 A 与配套产物 B 的误混用，不扩展为签名或逐对象证据系统。
- 应用指定计划的路径不得使用当前配置重新生成另一份计划或替换配套输入。PVE cloud-init 等前置写入必须使用与该计划一致的已准备输入；必要输入缺失或不匹配时，在设施写入前失败。前置写入的副作用须按 OPS-04 明示。
- 目标、执行版本及配套输入的检查在 snippets 上传前完成；state 是否已变化导致计划过期，保留 OpenTofu 获得原生 state 锁后的检查。计划过期时停止，不自动重新规划或重试旧计划，由调用方重新生成、审阅并授权。计划的保存或存在本身不代表部署授权，授权仍由调用方负责。
- 此能力针对 OpenTofu；不把 Ansible check mode 或设备 API 校验包装成可保存并重放的等价计划。

### 当前阶段的串行执行与失败边界

- 调用方已确认 CI 只允许单个任务串行运行；本轮保留现有 snippets 上传流程，以 OPS-08 的调用方约定保护完整变更流程，S3 原生锁继续保护 OpenTofu state。CI 串行机制与 state 锁各自保留，不互相替代。
- 本地检查、生成和 plan 可以独立运行；涉及 state 的 plan 同样遵守原生锁。本地实际变更须由调用方安排，避免与同一环境的其他变更重叠。
- 原生 state 锁不覆盖 OpenTofu 执行前的 SSH 上传。过期计划被拒绝前可能已上传、覆盖 snippets，因此失败不承诺零设施副作用；结果应说明已完成的前置步骤、失败步骤及已知副作用。
- 上传或验证失败时不继续 apply；apply 失败时保留实际结果和必要恢复产物，不自动回滚或重试。若仍需继续变更，由调用方检查现场并重新规划、审阅和授权。
- 新增共享执行锁、不可变 snippets 及相关清理机制不属于本轮范围；后期触发条件和备选方案见[路线图](roadmap.md#deferred-pve-concurrency-protection-beyond-serial-execution)。

## 4. 凭据、输出与状态

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| DATA-01 | 继续支持调用方注入环境变量和受保护文件 | 兼容外层 `op run` 与传统 CI Secrets；运行镜像不包含 `op`，不要求 1Password 服务 Token |
| DATA-02 | 按操作提供必要凭据 | 离线检查与生成不要求设施凭据；秘密不出现在命令参数、普通日志或报告中 |
| DATA-03 | 分离手写输入、生成物、诊断结果、敏感计划和临时文件 | 输出位置明确，敏感文件采用受限权限，不自动提交 Git |
| DATA-04 | 对需要版本管理的生成物提供明确导出方式 | 导出由调用方显式选择，不维护第二份手写配置 |
| DATA-05 | OpenTofu state 与锁保持独立生命周期 | 任务目录清理、容器重建和配置迁移不移动、删除或重建现有 state |
| DATA-06 | 生成结果可关联所选配置与运行时版本 | 提供简明版本及输入来源摘要，优先复用 Git revision、镜像 digest 和标准报告，不建立额外证据系统 |
| DATA-07 | 保留远程 state 写回失败时产生的本地恢复 state 或受保护紧急输出 | 以受限权限保留到调用方可访问、不会随任务清理消失的位置；报告失败及恢复位置，不输出 state 内容；本地恢复文件也写入失败时原始进程输出不得泄露到公开日志；保留失败时不得删除持有唯一副本的容器、卷或任务目录，也不得声称已完整恢复 |

### 已确定选型：S3 远程 state

- 本轮选择 OpenTofu `s3` backend；具体 S3 服务及连接参数由调用方提供，尚未选定服务产品。
- `iaas` 只维护配置契约、读取与校验逻辑及不含真实值的示例；实际 endpoint、region、bucket、key、workspace 等非秘密配置由调用方环境仓库维护并注入，不保存在本仓库或镜像内。
- 同一环境的同一 OpenTofu root，本地与 CI 必须读取调用方维护的同一份 backend 配置，使用相同的 endpoint、region、bucket、key 及 workspace；不同环境的 state 位置必须隔离。需要访问 OpenTofu state 的操作在缺少必要 S3 配置或 backend 初始化失败时必须停止，不得回退到临时本地 backend。
- 不访问 OpenTofu state 的 OPNsense、交换机、K3s 诊断或操作不要求 S3 配置和凭据；不得将 S3 初始化作为所有在线命令的统一前置条件。
- 启用 `use_lockfile=true` 原生 S3 锁；本地与 CI 使用同一锁，不以各自的任务目录或 CI 并发限制代替。锁冲突时等待或明确失败，不自动禁用锁或强制解锁。
- S3 凭据由调用方按 DATA-01 注入，与设施凭据分别声明、按需传入；离线检查和生成不连接 S3，也不要求 S3 凭据。
- bucket 由调用方预先准备并启用版本控制；state 和锁对象不属于任务临时资源，任务清理不得删除。现有 state 的迁移仍需单独审查，不随本轮适配自动执行。
- S3 写回失败后由 OpenTofu 生成的本地恢复 state 按 DATA-07 保留。这是失败恢复产物，不是切换到本地 backend；运行时不得自动推送该 state、强制覆盖远程 state 或重试 apply。恢复由调用方单独处理，本地 Docker 与 DinD 均须保留该恢复出口。
- 远程写回和本地恢复文件写入均失败时，底层工具可能将完整 state 输出到 stdout/stderr。state 变更子进程启动前须在容器内准备受保护的原始流捕获，禁止直连或 tee 到容器/终端/CI 日志；公共输出仅包含受控阶段/状态摘要，捕获内容以 0600 作为恢复材料保留。捕获无法准备时在变更前停止；运行中捕获失败不得回退公开输出，须保留已有内容及可用存储，并明确恢复材料完整性未确认。
- 若采用 S3 兼容服务，验收需覆盖代表性的 state 读写和原生锁条件写入、竞争行为；不能仅凭对象上传下载成功宣称兼容。实际服务验证仍受第 5 节测试环境与操作范围约束。

## 5. 架构兼容与交付

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| DIST-01 | 支持 Linux amd64 部署及 Apple Silicon Mac 的本地容器使用方式 | 明确容器引擎前提、平台选择和限制，不能静默选择不兼容架构 |
| DIST-02 | 评估并确定 Linux arm64 镜像支持范围 | 检查工具及 provider 兼容性；无法原生支持的操作明确标注，必要时显式使用 amd64 模拟 |
| DIST-03 | 提供启动器安装、升级、故障排查及配置迁移说明 | 文档由 `iaas` 唯一维护，`infra-ops` 只保存接入约定和环境值 |
| DIST-04 | 完成代表性验证 | 覆盖离线检查/生成、本地 Docker、Forgejo DinD、文件权限、路径传递及关键失败场景；未实际运行的平台不得标为已验证 |

真实本地 Docker、Forgejo DinD 和平台验证需另行明确测试环境与操作范围；
需求清单本身不授权连接共享环境或执行实际设施变更。
最小验收还应覆盖分组的路径解析与源文件保护、依赖不扩大范围、版本不兼容拒绝，
以及指定计划的保存/传递/应用和失效拒绝、同环境 A/B 计划与配套产物混用在 SSH 前拒绝。
针对本轮失败边界，覆盖代表性的前置上传失败阻止 apply、上传后计划过期的副作用报告、
远程 state 写回失败的恢复产物保留、本地恢复文件也写入失败时的受保护紧急输出、捕获失败不泄露且不虚报完整恢复，以及保留失败时停止清理，
并确认不访问 state 的在线操作无需 S3 配置。优先复用现有测试与可销毁环境，不展开逐对象矩阵；
这些验证不代表已实现本地与 CI 并发变更保护。

## 仓库责任

- `iaas`：配置契约、引用解析、启动器、执行适配、镜像、通用文档及测试。
- `infra-ops`：真实环境配置、场景、版本选择、S3 backend 配置与存储准备、凭据注入、受保护计划及恢复产物管理、完整变更流程的串行安排和部署授权策略。
- 调用方配置迁移需在接口设计完成后单独审查；不因运行时改造自动修改设备或现有 state。

## 本轮不包含

- 修改真实设备、迁移现有 state 或执行环境 apply。
- 建设通用 CMDB、配置平台、多租户或复杂继承系统。
- 将部署审批、秘密管理平台或 CI 调度器内置到运行时。
- 逐对象穷举验收、完整灾备或生产资格验证。

## 建议设计顺序

1. 配置入口与事实引用。
2. 输出、凭据、S3 state 与指定计划的生命周期约定。
3. 本地/CI 启动器。
4. 兼容迁移与架构支持。
5. 最小验收。
