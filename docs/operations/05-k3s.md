# 5. K3s：集群意图、部署与日常操作

本章定义 K3s 从已准备 VM 到初始集群的操作路径。它只管理 K3s-owned 文件和
服务；PVE VM、cloud-init、APT/Shell/Git、交换机、OPNsense 和基础服务仍由前述
章节负责。

## 5.1 当前状态与准入

**已实现：** 独立 intent 校验、与 generated PVE inventory 的组合、离线 review
渲染、主机 preflight、受保护 token 交接、串行 server/agent 部署、验证、节点
本地 embedded-etcd 快照和串行升级。

**未由当前仓库完成：** 调用方环境的 K3s VM/inventory/intent、Cilium 安装、
Flux、CSI、Gateway、工作负载、自动 restore、快照异地保留/删除、节点移除和
生产资格。测试 fixture 是 synthetic 数据，不能当作 实际环境部署证明。

开始前必须满足：

- [PVE](03-pve.md) 已为每台节点生成 inventory，并且 VM 已通过 guest verification；
- [VM Bootstrap](04-vm-bootstrap.md) 已提供 K3s 所需的来宾基线与出站路径；
- intent、生成的 PVE inventory、全体节点 scope、artifact/Registry/代理材料和
  受限权限 runtime JSON 已单独审查；
- 对 API endpoint、CIDR、控制面故障域、snapshot source、CNI 交接与故障恢复
  已作出明确决定。

## 5.2 输入、组合模型与节点网络

| 输入 | 所有权 | K3s 如何使用 |
| --- | --- | --- |
| K3s intent YAML | 操作者的 K3s 专用声明。 | 声明集群语义、版本、artifacts、Registry、proxy、snapshot 和节点角色。 |
| `$GENERATED_DIR/ansible/pve.yml` | PVE inventory 的生成物。 | 提供 SSH、架构与 NIC 事实；不能在 K3s intent 覆盖。 |
| runtime JSON | 仓库外受保护文件。 | 将 `op://` 引用解析给单个 `no_log` 动作。 |
| rendered review | `$OUTPUT_DIR/runtime/k3s/review.yml` 默认位置。 | 非秘密组合模型，供人工审查和 Ansible 使用；可删可再生。 |

PVE 源链为 `$ENVIRONMENT_DIR/inventory/pve-cluster.yml` 与
`$ENVIRONMENT_DIR/inventory/vms.yml` → 校验/归一化 → generated OpenTofu input
和 generated Ansible inventory → cloud-init → `vm_baseline` → K3s host handoff。
K3s intent 只叠加 K3s 所有的集群语义，不能向 PVE 源 inventory 复制或覆盖 node
事实。

部署阶段的 `k3s_prerequisites` 只接受 Debian/APT 主机，使用 `state: present`、
`update_cache: false` 安装 `ca-certificates`、`conntrack`、`iptables` 和 `socat`。
它不管理 APT source/凭据/proxy、主机网络、kernel policy 或 K3s 配置；这些分别
属于第 4 章和本章的其它受控步骤。

每个 K3s 节点必须在 generated `pve_vms.hosts` 中存在，并具备：

- `ansible_connection: ssh`、`ansible_host`、`ansible_user`；
- `pve_architecture`，目前支持的 K3s artifact 架构；
- `pve_nics`，其中**恰好一个**标为 `ansible_connection: true`；
- `pve_nics` 中**恰好一个** `role` 等于 `cluster.node_network_role`。

K3s 从这个选中 NIC 派生 `node_ip`、prefix、网络和接口名。不能将 storage/ingress
NIC 静默回退为 node identity。phase-one 推荐 `mgmt0` 负责 SSH/默认路由，
`cluster0` 负责 K3s node IP、server advertise address、etcd/Cilium underlay，
`storage0` 负责 TrueNAS，`ingress0` 负责 Gateway/VIP；非 `mgmt0` NIC 不应有
默认路由，除非另有经审查的策略路由设计。

## 5.3 K3s intent 参数

intent 根键严格为 `schema_version`、`cluster`、`nodes`，且 `schema_version` 必须
为 `1`。未知字段会被拒绝。

### 集群核心字段

| 路径 | 含义 | 约束/派生行为 |
| --- | --- | --- |
| `cluster.name` | 小写 slug 的集群名。 | 用于 snapshot 名等稳定标识。 |
| `cluster.version` | 精确 `vX.Y.Z+k3sN`。 | 所有 artifact URL 必须把同一版本作为路径段；升级不能降级或跳 minor。 |
| `cluster.datastore` | 数据存储模式。 | 当前只允许 `embedded-etcd`。 |
| `cluster.node_network_role` | 选取 PVE NIC 的通用 role。 | 例如 `cluster`；每节点恰好匹配一个 NIC。 |
| `cluster.cluster_domain` | Kubernetes DNS domain。 | 必须为 DNS 名；进入 `NO_PROXY`。 |
| `cluster.server_token_ref` | bootstrap token 的外部引用。 | 仅允许 `op://vault/item/field`；不含 token 值。 |
| `cluster.api_endpoint.mode` | `bootstrap` 或 `fixed`。 | `bootstrap` 使用 bootstrap server node IP；`fixed` 需要稳定 unicast IP 或 DNS。 |
| `cluster.api_endpoint.address` | fixed endpoint 地址。 | 仅在 `fixed`；不得等于任一 node IP，并进入 TLS SAN。 |
| `cluster.networking.pod_cidr` | Pod CIDR。 | 必须与 Service CIDR 同 IP family，不重叠且不与 VM 子网重叠。 |
| `cluster.networking.service_cidr` | Service CIDR。 | 同上；大小受实现的最大前缀限制。 |

embedded-etcd 要求一个 server，或奇数且至少三个 server；必须恰好一个
`bootstrap: true` server。每个派生 node IP 必须唯一，且 IP family 与 Pod/Service
CIDR 一致。

### artifact、组件、Registry 与服务代理

Artifact 下载主机和 URL 路径由调用方管理，不要求 URL 含版本目录，也没有特定
镜像站例外。组合模型仍要求精确 K3s version、HTTPS URL 和 SHA-256；下载后会运行
该二进制的 `--version` 并匹配完整版本。URL 名称本身不能证明实际版本。

| 路径 | 含义 | 约束/效果 |
| --- | --- | --- |
| `cluster.artifacts.<arch>.url` | K3s 二进制 HTTPS URL。 | 架构键必须刚好覆盖所有节点架构；URL 无 query/fragment，版本由下载的二进制验证。 |
| `sha256` | 二进制 SHA-256 checksum。 | 64 位小写十六进制；`get_url` 以其校验。 |
| `proxy_url` | artifact 下载 proxy。 | 可选非秘密 endpoint。 |
| `credential_ref` | artifact proxy 身份引用。 | 可选 `op://`；有它时在线动作必须有 runtime JSON。 |
| `components.external_cni` | 外部 CNI 策略。 | 当前必须为 `true`。 |
| `components.disable_network_policy` | 关闭 K3s 内建网络策略。 | 当前必须为 `true`，由外部 CNI 接管。 |
| `components.disable` | 禁用的内建组件。 | 当前必须刚好为 `servicelb` 与 `traefik`。 |
| `registry.fallback` | `allow` 或 `deny`。 | `deny` 需要版本支持且至少一个 mirror；避免 mirror 失败后静默打到默认上游。 |
| `registry.mirrors[]` | registry mirror 声明。 | 每 registry 唯一；详见下表。 |
| `service_proxy.state` | `present` 或 `absent`。 | absent 时不可声明 URL/credential；会仅清理角色托管 env 文件。 |
| `service_proxy.url` | K3s service HTTP(S) proxy。 | state 为 present 时必填。 |
| `service_proxy.credential_ref` | proxy 身份引用。 | 可选 `op://`；值只用于 node-side systemd env。 |
| `service_proxy.extra_no_proxy` | 额外 bypass 项。 | 仅明确 host/IP/有界 CIDR，拒绝过宽 public bypass。 |
| `snapshot.source_vm_ref` | 负责 etcd snapshot 的 server。 | 必须是已声明 server；目录固定派生为 `/var/lib/rancher/k3s/server/db/snapshots`。 |

每个 `registry.mirrors[]` 可含：

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `registry` | 被镜像的 registry 名。 | 唯一、受限 registry 名格式。 |
| `endpoint` | mirror HTTPS endpoint。 | 必须 HTTPS。 |
| `ca_ref` + `ca_sha256` | 自定义 CA 文件路径引用与预期 SHA-256。 | 两者必须同时存在。 |
| `auth_ref` | registry 用户名/密码 JSON 的外部引用。 | 可选；不写明文。 |
| `client_cert_ref` + `client_cert_sha256` + `client_key_ref` | mTLS 文件路径引用与 cert 校验。 | 三者必须全部存在或全部省略。 |
| `rewrites` | 受限 RE2 兼容 pattern → replacement 映射。 | 仅允许受限的 anchored prefix/capture 子集。 |

渲染后 role 管理 `/etc/rancher/k3s/config.yaml`、`registries.yaml`、
K3s/K3s-agent systemd env 和必要 TLS 路径引用。配置设置 `node-ip`、server 的
`advertise-address`、bootstrap `cluster-init` 或 join `server`、CIDR、domain、
`flannel-backend: none`、disable 项、TLS SAN 和必要时的 default-registry denial。
K3s 角色不触碰 APT source 或全局 shell/Git proxy。

### 节点列表

```yaml
nodes:
  - vm_ref: k3s-server-01
    role: server
    bootstrap: true
  - vm_ref: k3s-agent-01
    role: agent
    bootstrap: false
```

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `vm_ref` | generated PVE inventory host 名。 | 必须存在且唯一。 |
| `role` | `server` 或 `agent`。 | agent 不得为 bootstrap。 |
| `bootstrap` | 是否第一个 embedded-etcd server。 | 全集群恰好一个，且只能为 server。 |

## 5.4 密钥、scope 与离线审查

intent 中只存外部引用。runtime JSON 必须是仓库外普通文件、非符号链接、owner
可读且 group/other 无权限。密钥不得出现在 CLI、rendered review、inventory、
Ansible facts、普通临时文件、diff 或日志。

以下环境变量必须显式赋值；路径和节点名请替换为当前经审查的值：

```bash
export K3S_INTENT=/absolute/k3s-intent.yml
export OUTPUT_DIR=/absolute/output
export K3S_INVENTORY="$GENERATED_DIR/ansible/pve.yml"
export K3S_SCOPE='k3s-server-01,k3s-server-02,k3s-server-03,k3s-agent-01'
export K3S_RUNTIME_SECRETS=/safe/path/k3s-runtime.json

make k3s-check
make k3s-render
make k3s-ansible-syntax
make k3s-ansible-lint
```

`k3s-check` 和 `k3s-render` 不联系主机。必须审查 generated review，确认从 PVE
继承的架构、连接地址、node NIC、CIDR、endpoint、artifact、mirror、proxy、
snapshot source 和完整 node set，再进入在线操作。

`make check` 仍是仓库级离线总门禁；它不会执行 K3s preflight、部署、snapshot
或 upgrade，也不能替代本章的显式 K3s 证据。

## 5.5 部署、验证、快照与升级

| 操作 | 安全等级 | scope 规则 | 行为 |
| --- | --- | --- | --- |
| `make k3s-preflight` | 在线只读 | 可为明确节点子集。 | 检查 SSH、OS/架构、cgroups、能力、时间、接口、端口、磁盘、APT source、artifact、registry/TLS 与秘密可用性。 |
| `make k3s-verify` | 在线只读 | 明确节点且至少一个 server。 | 检查 K3s 服务、API/etcd 和节点注册；CNI 未初始化是可识别中间态，不是完整平台成功。 |
| `make k3s-deploy` | 变更 | 必须显式覆盖每个 declared node 一次。 | 重跑 preflight，bootstrap server，验证 API/token，再串行 join server 和 agent。 |
| `make k3s-snapshot` | 变更 | 必须只含 `snapshot.source_vm_ref`。 | 健康检查后写 root-only、节点本地 etcd snapshot。 |
| `make k3s-upgrade` | 变更 | 必须显式覆盖全体节点。 | 先生成 upgrade plan、重跑 preflight/snapshot，再 server 后 agent 串行升级。 |

部署前运行：

```bash
make k3s-preflight
make k3s-deploy
make k3s-verify
```

部署在 bootstrap API `/readyz` 返回 `ok` 前不会尝试 join；随后从 bootstrap server
以 `no_log` 临时读取活动 secure token 并与受保护外部引用核对。任何 preflight、
下载、服务启动、API/etcd 或 join 失败都会停止后续节点，不能靠缩小 deployment
scope 绕过。

升级还需声明：

```bash
export K3S_UPGRADE_TARGET='vX.Y.Z+k3sN'
export K3S_OBSERVED_VERSIONS=/safe/path/observed-versions.json
make k3s-upgrade
```

观察文件是非秘密 JSON，必须为 scope 中每个节点精确提供当前版本。planner 拒绝
降级、跳 minor、节点高于目标和不支持的混合版本，并渲染可审查的
`$OUTPUT_DIR/runtime/k3s/upgrade-plan.json`。snapshot 只是节点本地软件快照；当前没有自动
copy、retention、restore、uninstall、datastore replacement 或 node removal 命令。

## 5.6 CNI 与平台交接

初始配置有意设置 `flannel-backend: none` 并禁用内建 servicelb/Traefik，等待外部
CNI。当前自动化**不安装 Cilium**；因此 API、etcd 和 node service 成功后仍可能
处于 `CNI-not-initialized`。不得把此状态表述为工作负载网络、ingress、storage、
HA 或生产就绪。

在声称“可承载工作负载”前，必须另行完成和验证：Cilium underlay/Pod/Service、
Gateway/LB IPAM、TrueNAS CSI NFS/RWO 路径、Harbor 不可用恢复、DNS 故障路径、
Flux/bootstrap GitOps 与应用边界。这些是人工/后续平台阶段，详见
[全链路验收与恢复](06-acceptance-and-recovery.md)。

## 5.7 外部 platform repository handoff

IaaS 只交付非秘密 handoff bundle。它不安装 Flux、Cilium、CSI、Gateway、证书、
可观测性或应用资源，也不调用外部仓库 CI。准备一个仅含平台仓库 URL、明确 revision、
仓库相对路径和临时 bootstrap grant 外部引用的 handoff intent：

```bash
export PLATFORM_HANDOFF_INTENT=/safe/path/platform-handoff.yml
export PLATFORM_HANDOFF_OUTPUT=/safe/operator-path/platform-handoff.yml

make platform-handoff-check
make platform-handoff-render
```

`platform-handoff-check` 是离线校验，要求显式 K3s intent、generated inventory、
handoff intent 和完整 node scope，但不访问主机或写输出。`platform-handoff-render`
先以相同 model/scope 重跑 K3s 只读验证，再从唯一初始 server 读取 authoritative
server CA，验证 API endpoint 的 TLS/name，并以 `0600` 原子写入指定 operator path。
DNS endpoint 校验 DNS SAN，IPv4/IPv6 endpoint 校验 IP SAN；IPv6 连接地址使用方括号。
错误 CA 或身份不匹配会阻断输出，不会退回跳过 TLS 校验。
它是“基础设施只读 + 本地受保护 artifact 写入”，不属于 `make check`。

操作员必须显式将 bundle 交给外部 platform workflow。该 workflow 负责在自己的受
保护运行时解析独立、可撤销的临时 grant，比较其规范化 API endpoint 与 CA identity，
安装 Flux，验证第一次 reconciliation，并使该 grant 的集群侧认证失效；仅删除 secret
provider 中的值不足以完成撤销。bundle 的传输、发布、签名、CI 触发和上述平台消费步
骤都不由本仓库执行或背书；成功渲染不代表平台已完成交接或可投入运行。
